Версия 0.5 существенно лучше 0.3. Переработка не ограничилась точечными
исправлениями:

- файловые операции vault сведены в `VaultController`;
- привилегированные операции проходят через монопольный gate;
- временные файлы записи vault получили уникальные имена;
- версия схемы проверяется до любых изменений;
- связи канонизированы и закреплены `CHECK`;
- config получил явную схему типов и диапазонов;
- изображения проверяются по metadata до декодирования;
- устранён оставшийся N+1 в списке аккаунтов;
- backup получил fsync файла и каталога;
- главный модуль разделён на UI-mixin-модули;
- добавлены 10 тестовых модулей и 56 тестовых функций;
- Qt WebEngine/PDF удалены, размер exe снизился до 42 977 900 байт
  (около 41 MiB); компонентов Chromium в exe не обнаружено.

При этом три сценария потери или рассогласования данных остаются достаточно
серьёзными, чтобы не считать приложение готовым к хранению единственной копии
ценных секретов:

1. зашифрованный backup не аутентифицируется до удаления rollback;
2. смена пароля/recovery изменяет header в памяти до подтверждённой записи;
3. idle-lock отбрасывает несохранённые изменения формы.

Новые/оставшиеся находки:

- high: 3;
- medium: 5;
- low: 2.

## High

### [H5-01] Зашифрованный backup удаляет rollback до аутентификации

Файлы/строки:

- `backup.py:73-92`, `backup.py:121-162`;
- `crypto_store.py:130-177`, `crypto_store.py:202-217`;
- `dialogs.py:981-1003`;
- `main.py:580-589`.

`_is_valid_db()` для encrypted-кандидата выполняет только структурный `_parse`.
Это отсекает файл из одной сигнатуры и некорректные длины, но не проверяет GCM.
Достаточно изменить один байт `data_ct` настоящего backup:

- `_parse` успешно пройдёт;
- файл заменит рабочую БД;
- повторная `_is_valid_db(dst)` снова успешно пройдёт;
- rollback будет удалён в `finally`;
- только последующая разблокировка обнаружит повреждённый GCM-тег.

Такой же результат будет при корректном vault, пароль/recovery от которого
пользователь не знает. Диалог сообщает об успешном восстановлении до
подтверждённого открытия.

Исправление: encrypted backup должен проверяться через `crypto_store.unlock`
введённым мастер-паролем или recovery-кодом до замены. Rollback нельзя удалять,
пока восстановленный файл не аутентифицирован, десериализован SQLite и не прошёл
проверку схемы. Для UI удобно разделить операцию на:

1. выбор файла;
2. запрос секрета кандидата;
3. `unlock` + SQLite `quick_check`/schema check во временной БД;
4. атомарную замену;
5. повторное открытие рабочим кодом;
6. удаление rollback только после успеха.

Текущие тесты проверяют только `b"HRNKv1"` и plaintext-кандидаты. Сценарий
«валидный контейнер с изменённым ciphertext» отсутствует.

### [H5-02] Ошибка смены пароля/recovery оставляет новый header в памяти

Файлы/строки:

- `database.py:186-189`;
- `database.py:274-286`;
- `dialogs.py:356-394`;
- `vault_controller.py:189-220`.

`set_header()` сначала выполняет `self._header = header`, а затем `persist()`.
Если persist завершается ошибкой (ENOSPC, ACL, конфликт, сбой носителя), UI
показывает, что операция не выполнена, однако объект уже использует новый
header.

Последствия для смены мастер-пароля:

- файл на диске может остаться со старым паролем;
- память уже проверяет новый пароль;
- последующее успешное сохранение способно применить смену, хотя UI ранее
  сообщил об ошибке.

Для recovery ситуация опаснее: новый recovery-код при ошибке не показывается
пользователю, но остаётся в `_header`. Более поздний persist может незаметно
сделать известный recovery-код недействительным и записать неизвестный код.

Исправление: header должен обновляться транзакционно. Минимальный вариант:

```python
old_header = self._header
self._header = new_header
try:
    self.persist()
except Exception:
    self._header = old_header
    raise
```

Надёжнее сформировать контейнер с переданным `new_header`, записать его, и
только после успешного `os.replace` присвоить `self._header = new_header`.
Нужны fault-injection тесты отдельно для password и recovery.

### [H5-03] Idle-lock теряет несохранённые изменения открытой карточки

Файлы/строки:

- `ui_chrome.py:131-199`;
- `ui_account.py:26-64`, `ui_account.py:114-121`;
- `main.py:75-78`.

`_lock_screen()` сначала скрывает карточку, обнуляет `_current_account_id` и
сбрасывает `is_editing`, не вызывая `_stash_current_edits()`.

При успешной encrypted-блокировке затем дополнительно очищаются `_edit_cache` и
`_dirty_ids`. При plaintext-блокировке кэш не очищается, но текущие правки также
не были в него помещены. После выбора аккаунта данные перечитываются из БД.

При таймауте writer или ошибке persist `_lock_vault()` сообщает, что блокировка
отменена, но `_lock_screen()` уже скрыл форму и потерял контекст редактирования.

Исправление:

- до любых изменений UI сохранить текущую редактируемую карточку через
  `_stash_current_edits`;
- не очищать `_edit_cache` при автоматической блокировке;
- при неудаче блокировки полностью восстановить предыдущий UI/context;
- после разблокировки восстановить выбранный аккаунт и его cached edits.

Нужны тесты успешной и неуспешной idle-lock с изменённым, но не сохранённым
полем.

## Medium

### [M5-01] Откат restore выполняется прямым неатомарным copy поверх рабочей БД

Файл/строки: `backup.py:139-162`.

Rollback-копия создаётся durable, но восстанавливается через
`shutil.copy2(rollback, dst)`. Если процесс, диск или питание откажут во время
этого копирования, `dst` может остаться частично перезаписанным.

Rollback уже является полным отдельным файлом рядом с БД. Его следует
публиковать через `os.replace` либо копировать в новый уникальный temp с fsync и
только затем заменять `dst`. После отката нужно также синхронизировать каталог.

### [M5-02] Fast path доверяет только номеру схемы

Файлы/строки:

- `database.py:313-330`;
- `backup.py:93-118`.

Если `app_meta.schema_version == 7`, `create_tables()` немедленно возвращает и
не проверяет обязательные таблицы, колонки, индексы или FK. Повреждённая либо
частично скопированная БД с сохранённым номером версии откроется и упадёт позже.

Backup-проверка требует только `accounts`, `services`, `folders`; файл версии 7
без `gallery`, `linked_accounts` или других таблиц будет принят, после чего fast
path не восстановит структуру.

Исправление: дешёвая проверка schema fingerprint на fast path — полный набор
таблиц, критичных колонок/индексов и `PRAGMA foreign_key_check`. Для backup
версии 7 требуется тот же fingerprint.

### [M5-03] Цепочка миграции всё ещё не атомарна

Файлы/строки:

- `database.py:432-479`;
- `database.py:505-534`;
- `database.py:587-680`.

Проверка будущей версии теперь стоит правильно, но сама миграция содержит
несколько промежуточных `_commit()` и переключений `foreign_keys`. При сбое
между нормализацией данных, пересборкой таблиц, индексами и записью версии база
остаётся в промежуточном состоянии.

Большинство шагов идемпотентно, поэтому повторный запуск часто восстановится,
но это не эквивалент атомарной миграции. Нужны миграции по версиям с явными
границами транзакций и fault-injection тестами после каждого DDL-шага.

### [M5-04] Большой файл изображения полностью читается до проверки лимита

Файл/строки: `widgets.py:421-427`, `widgets.py:486-497`.

Лимит 15 МБ проверяется после `f.read()`. Выбор файла размером в гигабайты
сначала пытается полностью загрузить его в память.

Следует проверить `os.stat().st_size` до чтения, затем читать не более
`MAX_IMAGE_BYTES + 1`. Для clipboard действуют отдельные ограничения Qt.

Остальная часть M3-05 исправлена качественно: metadata читается до decode,
задан allocation limit, есть лимиты количества и суммарного объёма.

### [M5-05] Полная serialize остаётся в GUI без debounce

Файлы/строки: `vault_controller.py:87-135`, `database.py:153-174`.

Шифрование и I/O выполняются в worker, однако `conn.serialize()` по-прежнему
копирует весь vault в GUI-потоке после каждого оборота event loop с изменениями.
Для базы с сотнями мегабайт gallery это означает паузу интерфейса и временную
вторую полную копию БД в памяти.

Это уже не дефект малой базы, но M-08 нельзя считать полностью закрытым для
масштабирования. Практичный следующий шаг — небольшой debounce и измерение
времени/памяти serialize на 100–500 МБ. Более глубокое решение — архитектура без
полной перезаписи контейнера при каждой правке.

## Low

### [L5-01] Ошибка вычисления общего размера галереи отключает лимит

Файл/строки: `widgets.py:515-527`.

Исключение provider подавляется с `other = 0`. При ошибке БД лимит 500 МБ
становится fail-open. Безопаснее запретить добавление и показать ошибку либо
использовать последнее успешно вычисленное значение.


Оставшиеся ограничения:

- mixin-слои всё ещё не имеют явных интерфейсов зависимостей и обращаются к
  динамическим полям `self`;
- SQLite `conn/cursor` типизированы как optional, но основные ошибки типов для
  них глобально подавлены в mypy;
