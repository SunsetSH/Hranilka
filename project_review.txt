--------------------------------------------------------------------------------
1. КРАТКОЕ РЕЗЮМЕ
--------------------------------------------------------------------------------
«Хранилка» — оффлайн-менеджер учётных записей (PySide6 + SQLite + qasync,
~9200 строк). Качество кода существенно выше среднего: криптоядро
(Argon2id + AES-256-GCM, envelope-схема) реализовано образцово, SQL полностью
параметризован, миграции защищены pre-migrate-копиями, бэкап/restore имеют
валидацию и откат, тесты (97 шт.) проходят, строгий mypy для data-слоя чист.

Главный риск — НЕ в криптографии, а в том, что она по умолчанию ВЫКЛЮЧЕНА:
при дефолтной конфигурации все пароли, секретные ответы и recovery-фразы лежат
на диске открытым текстом (и размножаются авто-бэкапами). Второй блок проблем —
масштабируемость (вся БД сериализуется и шифруется целиком при каждом
сохранении; BLOB картинок в БД) и синхронные операции в UI-потоке.

Итог по уровням риска: CRITICAL — 2, HIGH — 11, MEDIUM — 17, LOW — 15.

--------------------------------------------------------------------------------
2. ОБЩАЯ ОЦЕНКА СОСТОЯНИЯ ПРОЕКТА
--------------------------------------------------------------------------------
Оценка: 7.5/10 — «хороший pet-проект, близкий к продакшн-качеству ядра,
с одним архитектурным риском безопасности (plaintext по умолчанию) и
потолком масштабируемости».

Сильные стороны (подтверждено кодом):
+ crypto_store.py: envelope-шифрование, DEK + два wrap'а (пароль, recovery),
  свежие nonce/соли на каждую операцию, жёсткая валидация недоверенного
  заголовка ДО запуска Argon2 (защита от KDF-DoS), точечный InvalidTag ->
  WrongPassword без маскировки MemoryError.
+ SQL-инъекции отсутствуют: 100% значений через ?-плейсхолдеры; f-string
  подставляют только внутренние идентификаторы.
+ Атомарная запись (mkstemp+fsync+os.replace) для БД и config.json;
  secure_delete=ON; PRAGMA foreign_keys=ON.
+ Миграции: read-only определение версии, FutureSchemaError против даунгрейда,
  durable pre-migrate-копия, канонический порядок пересборки таблиц.
+ Бэкап: fsync файла и каталога, ротация только после успеха, полная
  валидация кандидата на restore (quick_check, foreign_key_check, версия
  схемы), страховочная *.pre-restore-копия с авто-откатом.
+ Продуманная async-модель (RLock + single-worker executor + writer-поток,
  поколения сессий _session_gen / StaleSessionError).
+ Чистый импортный граф без циклов; UI не лезет в SQL; крипто изолировано.
+ Репозиторий чист: ни БД, ни config.json, ни секретов в git (43 файла,
  только исходники и тесты). Защита от CSV/formula-injection в экспорте.
+ Тесты изолированы (tmp_path, offscreen), реальных секретов не содержат.

Слабые стороны:
- Шифрование по умолчанию выключено -> plaintext-хранение секретов (см. §3).
- Whole-DB serialize+encrypt на каждое сохранение + BLOB в БД = потолок
  масштабируемости и постоянный RAM = размер всей БД.
- Ряд синхронных операций (BLOB, запись при drag&drop) в UI-потоке.
- Пробелы в тестах критичных security-путей (смена мастер-пароля, ротация
  recovery, GCM-tamper).
- .gitignore, README.md и assets/ не закоммичены — свежий клон неполон.

3. КРИТИЧНЫЕ ПРОБЛЕМЫ (CRITICAL)
--------------------------------------------------------------------------------
C-1. БД по умолчанию не шифруется — все секреты открытым текстом на диске
  Файлы: config.py:79 ("encryption_enabled": False), database.py:161-172
  (connect), database.py:929-937 (add_account пишет password как есть).
  Описание: при дефолтной установке hranilka.db — обычный SQLite: колонки
  accounts.password, secret_questions.answer, recovery_phrases.phrase,
  recovery_codes.code читаются любым, кто получил файл
  (sqlite3 hranilka.db "SELECT login,password FROM accounts").
  Почему важно: это менеджер паролей; ожидание пользователя — «данные
  защищены». Доступ к файлу = полная компрометация всех учёток (другой
  пользователь ОС, вредонос, облачная синхронизация папки, бэкап ОС).
  Последствия: тотальная утечка всех секретов при доступе к диску.
  Риск: CRITICAL (в дефолтной конфигурации).
  Рекомендация: включить шифрование по умолчанию (мастер-пароль на первом
  запуске) ЛИБО постоянный заметный баннер «БД НЕ зашифрована — любой с
  доступом к файлу прочитает пароли» + предупреждение на первом запуске.
  Минимум — явно задокументировать.

C-2. Бэкапы наследуют plaintext-режим, авто-бэкап включён
  Файлы: backup.py:39-62 (create_backup — побайтовая копия), main.py:135-158
  (авто-бэкап при закрытии), config.json:15 (backup_auto_on_close: true).
  Описание: бэкап копирует файл «как есть»; при выключенном шифровании до
  backup_keep_count (5) plaintext-копий всех паролей появляются в
  пользовательской папке (часто — облачно-синхронизируемой) без предупреждения.
  Последствия: тиражирование секретов по диску/облаку.
  Риск: CRITICAL (в дефолтном режиме; при включённом шифровании — не проблема).
  Рекомендация: предупреждать, что бэкап незашифрованной БД содержит секреты
  открытым текстом; предложить шифрование бэкапа отдельным паролем.

4. ПРОБЛЕМЫ ВЫСОКОГО ПРИОРИТЕТА (HIGH)
--------------------------------------------------------------------------------
H-1. Экспорт пишет пароли/фразы/коды открытым текстом без предупреждения
  Файлы: export.py:105-106, 127-131, 166-379; пароль входит в include_basic
  (включён по умолчанию).
  Последствия: постоянный plaintext-артефакт вне защиты приложения (особенно
  HTML — самодостаточный дамп с base64-картинками).
  Риск: HIGH. Fix: модальное предупреждение перед экспортом секретов;
  галочку «Пароль» по умолчанию снять.
  (Отмечено хорошее: _csv_safe (export.py:71-80) корректно защищает от
  CSV/formula-injection и применяется к CSV и XLSX.)

H-2. Нет ужесточения прав доступа (ACL) к файлам с секретами
  Файлы: database.py:215-239 (_atomic_replace), backup.py:17-21,
  config.py:155-163. Grep icacls/chmod/SetFileSecurity — 0 совпадений.
  Описание: hranilka.db, бэкапы, config.json и временные копии наследуют ACL
  каталога. На многопользовательской Windows или при установке в общий путь
  файл читается другими пользователями.
  Риск: HIGH (усугубляет C-1/C-2). Fix: DACL «только текущий пользователь»
  (win32security / icacls /inheritance:r /grant:r) для БД, бэкапов, temp-копий.

H-3. Временные plaintext-копии всей БД остаются на диске без затирания
  Файлы: database.py:653-682 (*.pre-migrate), main.py:665-667 (*.pre-restore),
  backup.py:148-149 (*.restore-tmp, *.rollback), main.py:530-542 (*.locked-TS).
  Описание: полные копии БД при миграции/восстановлении; удаляются обычным
  unlink (без перезаписи), часть намеренно остаётся. secure_delete=ON действует
  только внутри самого SQLite-файла.
  Риск: HIGH в plaintext-режиме. Fix: ACL + best-effort перезапись перед
  удалением; документировать *.locked-* / *.recovery как чувствительные.

H-4. Вся БД сериализуется и шифруется целиком при КАЖДОМ сохранении;
     картинки-BLOB в БД
  Файлы: database.py:254 (conn.serialize()), :259-268 (cs.seal), :215
  (_atomic_replace — запись всего файла).
  Описание: стоимость сохранения = O(размер всей БД), не O(изменений). Вся
  расшифрованная БД (включая все BLOB галереи) постоянно живёт в RAM
  (:memory:). Текущая БД пользователя уже 33 МБ; при сотнях МБ галереи каждое
  сохранение = сериализация + AES-GCM + запись сотен МБ.
  Последствия: деградация каждого сохранения, RAM = размер всей БД.
  Риск: HIGH (архитектурный потолок). Fix: вынести BLOB в отдельные
  зашифрованные файлы (per-image), либо инкрементальное сохранение; минимум —
  документировать практический лимит объёма.

H-5. Хрупкий инвариант блокировок: serialize_db обязан оставаться под RLock
  Файлы: database.py:1689 (_DB_NO_LOCK: serialize_container, persist,
  seal_and_write, flush), :254-256.
  Описание: незалоченные flush/persist из writer-потока корректны ТОЛЬКО пока
  serialize_db не попал в _DB_NO_LOCK. Инвариант нигде не закреплён — одна
  строка в списке ломает потокобезопасность conn.
  Риск: HIGH (по хрупкости, не по текущему багу). Fix: тест/assert, что
  "serialize_db" not in _DB_NO_LOCK; комментарий-инвариант у списка.

H-6. Тихая потеря картинок при сохранении, если BLOB не дочитался лениво
  Файлы: database.py:1478-1484 (save_account: DELETE FROM gallery + INSERT),
  widgets.py:1088-1097 (get_data: элемент с data=None молча выбрасывается).
  Описание: галерея перезаписывается целиком из данных виджета; если ленивая
  дозагрузка BLOB вернула None (ошибка чтения/потерян loader) — картинка
  безвозвратно удаляется из БД при сохранении карточки.
  Риск: HIGH (потеря пользовательских данных). Fix: при неудачной дозагрузке
  сохранять запись по image_id без изменения BLOB либо прерывать сохранение.

H-7. Синхронная загрузка BLOB в UI-потоке при клике по миниатюре
  Файлы: widgets.py:987-1001 (_on_thumb_click -> _load_lazy_bytes ->
  db.load_gallery_image синхронно), :1018, :1096.
  Последствия: видимый фриз UI на крупных BLOB (до 15 МБ).
  Риск: HIGH. Fix: async-корутина + run_in_executor (по образцу
  _preload_pipeline).

H-8. Синхронные записи в БД в UI-потоке при drag&drop и операциях дерева
  Файлы: ui_tree.py:150-175 (set_*_order при каждом drop), :412-416
  (_set_favorite), rename/move/delete/add — синхронно; ui_account.py:432
  (get_all_accounts синхронно).
  Риск: HIGH при больших БД. Fix: util.fire(...) + db.run_async.

H-9. Синхронное чтение всего зашифрованного контейнера при старте
  Файл: main.py:580 (f.read() всего файла до показа UnlockDialog).
  Риск: HIGH при большой БД (блокирует запуск). Fix: чтение в фоне, сразу
  показывать окно ввода пароля.

H-10. Захардкоженные цвета в галерее нарушают требование кастомизации темы
  Файлы: widgets.py:916, 929, 932, 936, 725-726 (#333, #FFC400, #AAAAAA,
  #808080).
  Описание: CLAUDE.md требует настраиваемость цветов текста/фона; на кастомных
  темах плейсхолдеры миниатюр нечитаемы/невидимы.
  Риск: HIGH (нарушение требования). Fix: брать цвета из config
  (text_color/tree_bg_color).

H-11. Нет критичных security-тестов: смена мастер-пароля, ротация recovery,
      GCM-tamper, VaultConflictError, lock/unlock-цикл
  Файлы: tests/test_crypto_store.py, tests/test_vault.py — отсутствуют тесты
  для crypto_store.py:223-237 (change_password), :240-249
  (regenerate_recovery), :216-219 (tamper), database.py:196-213
  (_check_no_external_change), :297-314 (lock).
  Последствия: регрессия смены пароля/ротации recovery/детекции подделки
  останется незамеченной — это самые дорогие сбои для менеджера паролей.
  Риск: HIGH. Fix: см. §12, топ-5 недостающих тестов (с примером кода).
